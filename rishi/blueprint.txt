For your project, I would **not chunk first and then build hierarchy**.

Instead:

```text
Raw Notes
    ↓
Hierarchy Extraction
    ↓
Tree of Topics/Subtopics
    ↓
Attach Original Paragraphs
    ↓
Generate JSON
```

If you chunk first, you lose structure.


Then:

```text

```

as level 2.

Then:

```text

```

as level 3.

Then attach paragraphs under the nearest heading.

# For Your Learning Graph

I would actually generate two files:

### hierarchy.json

```text
Used by frontend
```

```json
{
  "UNIT 1":
  {
    "Entrepreneurship":
    {
      "Characteristics": {}
    }
  }
}
```

---

### chunks.json

```text
Used by RAG
```

```json
[
  {
    "chunk_id":"c001",

    "node_path":[
      "UNIT 1",
      "Entrepreneurship",
      "Characteristics"
    ],

    "original_text":
    "An entrepreneur should be innovative."
  }
]
```

---

### graph.json

```text
Used by recommendation engine
```

```json
{
  "nodes":[...],

  "edges":[
    {
      "from":"Characteristics",
      "to":"Innovation",
      "type":"related"
    }
  ]
}
```

This three-file approach is much cleaner than trying to force hierarchy, RAG chunks, and recommendation relationships into a single giant JSON.

For your project, I would **strongly recommend a Python pipeline, not manual JSON creation through an LLM**.

Looking at your uploaded notes, there are already hundreds of headings, subheadings, lists, case studies, entrepreneur examples, myths, characteristics, leadership styles, etc. 

If you manually send chunks to an LLM:

```text
Part 1 → JSON
Part 2 → JSON
Part 3 → JSON
...
```

you will eventually get:

* inconsistent hierarchy depths
* duplicate nodes
* naming variations
* broken parent-child relationships
* impossible maintenance when notes change

Your architecture deserves something more robust.

# Antigravity Prompt

Use this prompt to build the **Knowledge Compiler**.

```text
You are a Knowledge Compiler.

Your job is NOT to summarize.

Your job is NOT to teach.

Your job is NOT to simplify.

Your job is to convert educational material into a lossless hierarchical knowledge structure.

ABSOLUTE RULES:

1. Preserve every original word.
2. Never paraphrase.
3. Never summarize.
4. Never remove examples.
5. Never remove lists.
6. Never merge unrelated sections.
7. Never generate new educational content.
8. The original text must remain recoverable 100%.

GOAL:

Convert the document into a hierarchy suitable for:

- Fog-of-war learning
- Expandable knowledge trees
- RAG retrieval
- Interactive node exploration
- Concept graph generation

OUTPUT SCHEMA:

{
  "id": "",
  "title": "",
  "node_type": "",
  "path": [],
  "children": [],
  "content": [],
  "metadata": {}
}

NODE TYPES:

course
unit
topic
subtopic
concept
case_study
example
activity

RULES FOR HIERARCHY:

- Major units become unit nodes.
- Major headings become topic nodes.
- Subheadings become subtopic nodes.
- Lists may become concept nodes.
- Case studies become case_study nodes.
- Activities become activity nodes.

CONTENT RULES:

Store original text ONLY inside content arrays.

Example:

{
  "title": "Characteristics of Successful Entrepreneurs",
  "content": [
      "Discipline",
      "Curiosity",
      "Creativity"
  ]
}

Do not rewrite.

Do not modify punctuation.

Do not remove formatting information.

GRAPH EXTRACTION RULES:

Additionally generate:

{
  "concepts": [],
  "relationships": []
}

Relationship types:

prerequisite
related_to
example_of
part_of
causes
supports

Only extract relationships explicitly implied by the material.

FOG-OF-WAR SUPPORT:

For every node calculate:

{
  "expandable": true,
  "content_available": true,
  "child_count": 5
}

NODE IDENTIFIERS:

Generate stable IDs using:

unit.topic.subtopic

Example:

unit1.entrepreneurship.characteristics

OUTPUT FILES:

1. hierarchy.json
2. graph.json
3. chunk_map.json

chunk_map.json must map every paragraph to the node that owns it.

LOSSLESS REQUIREMENT:

If all content arrays are concatenated together, the original document should be reconstructable with no missing educational content.

Return ONLY valid JSON.
```
